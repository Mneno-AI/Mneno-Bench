## Canonical identity and persistence specification

Use canonical sorted JSON hashed with SHA-256, distinct from timestamp/UUID attempt ID. Quality experiment identity comprises dataset bytes/upstream revision, normalized input hash, ordered selected question IDs, parser/formatter revision, metric/prompt revisions, ingestion and session rules, malformed-reference policy, seeds, system config, top-k/candidate limits, explicit token budget and token estimator/tokenizer version, cache mode/capacity/key semantics, Bench source hash, Core build/wheel hash and capability contract, requested/resolved provider model and endpoint/deployment revision where available. Record dependency lock/runtime/platform. For latency/reliability identity also include worker/backend, rate limits, concurrency, timeout/retry policies and hardware/resource limits. Changes to these can preserve a paired quality question set but cannot imply efficiency comparability.

Do not hash credentials. Save a redacted resolved manifest before execution, immutable per-attempt/segment directory, phase-specific retrieval/evaluation hashes and timestamps, atomic per-case files linked to original raw/trace hashes and mapping export. Required phase completion includes requested providers and judge state, not merely the presence of a case file. Validate format/schema/hash, case ID/index/query/input, configuration, phase and referenced artifacts before reuse. Conflicting duplicates fail clearly. Missing manifests are unsafe for controlled resume. Lock active directories; latest projections update only after validated report generation and link immutable artifacts. Recompute aggregates with availability denominators and unique status counts before publication. Preserve old artifacts and never silently rewrite historical scores.

## Controlled comparison protocol

1. Obtain a legal local LOCOMO copy, record upstream revision and raw checksum. Freeze loader/formatting, all ordered questions and annotation-warning policy before experiments. Keep category 5/evidence-free questions visible but explicitly outside evidence-recall denominators.
2. Fix an agreed k and token budget grid before observing results (suggest k=5 and 10, context budgets 1,024 and 4,096 estimated tokens). These are future experimental choices, not current default guarantees. Use identical question/input/session rules. Keep Full Context unbounded and labeled separately. Do not equate candidate count with token budget.
3. Run Keyword and current deterministic Mneno as anchors. Compare future FTS5/BM25, hybrid and semantic variants only when Core independently supplies them. Record effective algorithm/settings/capabilities; if SDK cannot express a budget or algorithm, mark that comparison unavailable. Preserve framework definitions for every old/new Core build; no benchmark-specific Core tuning.
4. Pair old/new results on identical questions and availability masks. Report per-question differences, macro recall, micro recovered/expected evidence, hit rate and inclusion recall, by category/conversation. Report uncertainty over independent conversations (e.g. fixed-seed cluster bootstrap), not treating correlated turns as independent. Freeze analysis code/seed before results. Also show full requested-set execution counts so dropping failures cannot improve apparent quality.
5. Use workers=1 for timing, same machine/runtime/CPU/RAM limits and workload order; separate fresh ingestion, process cold reopen, warm retrieval and cache modes. Repeated deterministic runs check identity/stage equivalence; timings use distributions. Throughput runs with parallel workers are a separate experiment.
6. Publish three reports: retrieval quality (stage-specific metrics and evidence), resource efficiency (latencies, CPU/RAM/storage, context estimates, token usage/cost estimates), operational reliability (errors, retries, skips, completion and cache ledger). Do not combine them into an opaque score. Optional external NIM is a separate production variant; internal regression suite is separate from external validation.
7. Compare providers only under matched requested task and cache/budget policy. Record external network latency and billing where measurable. A nondeterministic endpoint is not made reproducible by temperature zero; preserve responses and model identity.

Phase B acceptance gate: P0 items pass focused tests, manifests reproduce aggregate numerators/denominators, interruption/resume matches uninterrupted quality with documented cache differences, Core provides the versioned capability contract, matched fixtures/inputs and artifacts are available, and the user approves actual experiments and their external-call budget. No quality or 4 GB claim before these gates and measurements.

## Resource-constrained procedure

CPU-only ~4 GB is a hypothesis. Use a fixed CPU-only Linux container/VM with 4 GiB enforced memory, explicit CPU quota, no accelerator devices, and an OS/process-tree sampler. Record OOMs and swap policy; a Docker limit on a larger host alone does not prove all ordinary laptops behave identically. Keep local deterministic and external-provider paths separate.

Suggested future workload tiers: 48-memory Context Rot smoke regression; LOCOMO individual conversations and the full 5,882-message inventory treated as isolated conversations; 1,000 and 10,000 memory scaling subsets drawn by a frozen deterministic procedure from existing legally available inputs, with no annotation changes. Do not claim 10,000 unique LOCOMO messages exist: larger collections require separately approved input availability and provenance; avoid duplicates presented as new evidence.

Measure ingestion in three fresh stores, DB/index/WAL size after consistent checkpoint, cold process open/reopen latency (explicitly distinguish OS page-cache cold from process cold), then 20 warm-up queries and at least 100 measured retrieval and context calls per tier in fixed order. Report p50/p95 with sample count/quantile method, wall and CPU times, simultaneously sampled RSS plus OS peak, successful inserts/second and failure/OOM counts. Repeat three independent runs; cache-enabled and cache-disabled measurements separate. Retain representative traces; trace-enabled overhead should be separately characterized. Persistent reopen support and index identity depend on Core; do not build a Bench storage engine.

## Provider audit and future Codex requirements

NIM's verified code path is a reranker injected into `MemoryClient` by `_build_mneno_reranker` through `LLMClient.rerank`. No Bench embedding call exists. No NIM answer-generation path exists; deterministic extraction creates candidates. NIM can separately be configured as optional judge through `LLMClient.generate`, but retained run is retrieval-only and judge not requested. `.env` alone does not enable network traffic: model configuration and `allow_external_calls` gate execution; environment can supply credentials/base URL. No secret values were read for this audit.

Current YAML requests `nvidia_nim/nv-rerank-qa-mistral-4b:1`, hosted ranking endpoint, 50-document prefix, 4,096-entry query+ordered-content LRU per conversation, 60-second timeout, two retries, 30 requests/minute and one concurrent call. Saved run used 60 requests/minute, so current YAML cannot be called its exact historical profile. Saved invocation reports 3,175 attempts, 3,166 successes, nine retries, zero terminal failures/429s, 347 hits and 158,300 documents; 815 resumed cases mean totals omit earlier segments. Limiter is shared by threads; retryable errors use status/connection detection, exponential backoff/jitter or Retry-After; LiteLLM rerank internal retries disabled. Exceptions eventually fail a question if propagated; initialization errors are swallowed, and SDK handling/fallback cannot be verified without installed Core. Provider call latency and actual deployment model are absent; logical cache misses are not billable-attempt counts.

Codex SDK is **not implemented or assumed compatible with LiteLLM**. During a future integration, verify official SDK interface and available model IDs at that time. No `gpt-6.1-luna` availability is asserted. It would need a shared provider boundary in `common/llm_client.py` compatible with the judge's generate contract, with an additive structured usage/result envelope rather than SDK-specific runner logic. Allowed prospective modes: optional judge; separately approved answer-generation evaluation. Retrieval-only must remain unaffected and credential-free; do not use Codex responses to manufacture retrieval evidence or candidate labels.

Require requested/resolved model ID and SDK version, provider/session/request IDs, prompt version, usage input/output/cached tokens when exposed (null otherwise), latency, retry attempt/error/status and skip reason. Test missing credentials, incompatible model, timeout, malformed response, partial usage and retry exhaustion with local fakes. Preserve raw nonsecret responses; no model identifier accepted merely from a guessed string. If transport cannot fit the current text-only client, add an explicit shared adapter design first rather than pretending it is a drop-in provider.
